# Check commit and merge-message attribution

Commit messages must not contain co-author or assistant attribution. Check a
message file before committing:

```sh
python3 scripts/check-attribution.py message commit-message.txt
```

The checker rejects these case-insensitive line prefixes, including indentation
and spaces before the colon:

- `Co-authored-by:`, `Authored-by:`, `Generated-by:`, `Assisted-by:`
- `AI-assisted-by:`, `AI-generated-by:`, `AI-model:`, `AI-agent:`
- `Model:`, `Agent:`
- `Generated by`, `Generated with`, `Written by`, `Written with`, `Authored by`,
  `Authored with`, `Assisted by`, or `Assisted with`, optionally prefixed by `🤖`.

A matching line anywhere in the message fails, including inside a quoted example.
The error prints its location, never the untrusted message text. Ordinary prose
such as "Reject Co-authored-by trailers" passes.

## PR checks

`attribution-self-test` runs the checker tests and checks the current PR using a
read-only token. It runs on every PR, including docs-only changes. It is an
unprivileged test of the proposed checker, not the trusted enforcement status.

`trusted-attribution` runs on `pull_request_target`. It checks out only the trusted
default branch, never a PR or fork ref, and does not run PR code. Its token can
read contents and PR metadata and write commit statuses. It posts
`commit-attribution` on the PR head. Make that status required on protected
branches after installing the workflow on the default branch. The trusted
workflow cannot protect its own first installation: GitHub must first have the
workflow and checker on the default branch.

The checker compares immutable base/head SHAs with paginated GitHub responses.
It checks every returned commit message, including non-head and merge commits,
and verifies the unique commit count against PR metadata. This uses the paginated
comparison endpoint because the PR-commits endpoint stops at 250 commits. Missing
pages, duplicate commits, API errors, a different head, or changed PR metadata fail
the check. PR titles and bodies are also checked because they can enter generated
merge messages. Message text is passed as data, never interpolated into shell code.

GitHub exposes no pre-merge event containing an arbitrary future message typed
into its merge UI. A green status on a head SHA does not freeze future PR text or
UI edits. Editing PR text schedules another check but is not atomic with merging.
Use the explicit payload procedure below for the actual proposed message.

## Owner merge procedure

Only the owner merges. This helper validates attribution; it does not replace the
exact-head review, green checks, thread resolution, or other merge gates.

Prepare an explicit payload from the PR's current title and body, replacing `PR`
with its number:

```sh
gh api repos/moonbase2090/Scorecard/pulls/PR \
  --jq '{sha: .head.sha, merge_method: "merge", commit_title: .title, commit_message: (.body // "")}' \
  > proposed-merge.json
python3 scripts/check-attribution.py merge --pr PR --payload proposed-merge.json
```

Review the file's exact title, body, method, and full head SHA. The SHA must match
the reviewed merge packet. The validator accepts explicit `merge` and `squash`
payloads, but Scorecard permits execution only with `merge`. An explicit empty
`commit_message` is valid. Omitted, extra, or duplicate fields fail. No defaults
are left for GitHub to compose from unchecked text.

The command above validates only the exact proposed payload locally. It makes no
network request and submits nothing. Once every merge gate passes, the owner can
submit it:

```sh
python3 scripts/check-attribution.py merge --pr PR --payload proposed-merge.json --execute
```

Execution validates all current PR commits and checks that the live head matches
the payload SHA. The helper checks `gh` is authenticated as the owner and sends
the same in-memory JSON that it validated, with `sha`,
`commit_title`, and `commit_message` explicitly set. It never rereads the file
between validation and submission, requests no rule bypass, and does not use
admin overrides. The synchronous API supports ordinary direct merges, not merge
queues or stacked PRs; those paths need an equivalent exact-message validator.

The server still controls the final commit representation. The helper checks the
returned commit message after a successful merge. If GitHub adds prohibited text,
that check detects it after the merge and reports failure; it cannot prevent or
undo the server's change. Inspect the history and report it without rewriting it.
Do not replace the validated merge with a UI merge or another command that
regenerates the message.

## Verify the checker

```sh
python3 scripts/test-check-attribution.py
```

Tests exercise the real CLI. The isolated GitHub transport returns controlled
API data; no test makes a real merge request. Cases include a historical squash
message, a prohibited non-head commit, 301 commits across four pages, missing
pages, metadata races, exact payload substitution, and untrusted shell/workflow
commands. The existing historical commit remains unchanged.
